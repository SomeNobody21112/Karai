# CLAUDE.md — mplads-intel

Read this first, every session. Do not re-read the whole repo.

## What this is

An AI-assisted monitoring layer over MPLADS/eSAKSHI work-lifecycle data. It learns what
normal work looks like across the national portfolio, compares each work against its true
peers, predicts completion risk, detects behavioural change, fuses those signals into an
explainable case file, and ranks case files by audit return-on-investment.

SIH 2026 · PS 26102 (MoSPI) · Team Morior Invictus.

## The five hard constraints

These are product constraints, not style preferences. They must survive into the code and
the UI copy.

1. **No fraud verdicts.** Output is an *investigation lead* with evidence. No field,
   variable, column, or label anywhere may be named `fraud_probability`, `is_fraud`,
   `fraud_score`, or `fraudulent`. Enforced by `test_no_fraud_language_in_the_source_tree`.
2. **No fraud classifier.** There are no fraud labels in the data. Any supervised model
   claiming to predict fraud is fabricated. Scoring is transparent, weighted, rule-based.
3. **Silhouette is not accuracy.** Never presented as such — in code comments, docs, UI, or
   slides. Ours runs ~0.04–0.05; say so.
4. **`ACTUAL_AMOUNT` is not expenditure.** 98.35% of completed works have it exactly equal
   to `RECOMMENDED_AMOUNT`. No overrun or underspend signal exists. See DATA_CONTRACT §4.6.
5. **Human-in-the-loop.** Every recommendation ends in "a human should check X", never
   "this is an issue".

## Conventions

- Type hints on every function. `pathlib`, never string paths. No notebooks in `src/`.
- **Never hardcode a path, a seed, or a date.** Import from `mplads.config`.
- Every phase writes to `data/artifacts/`; expensive work is cached and skipped on rerun.
- Every transform logs its row count at entry and exit. **No silent drops, ever** — rows
  are dropped only with a logged reason and a counter.
- Deterministic: reruns produce byte-identical output. Dedup sorts on a stable secondary
  key so results do not depend on input file order.
- `Dataset/` is read-only. Never write into it.

## Data facts you must not get wrong

Full detail in `docs/DATA_CONTRACT.md`. The ones that bite:

- **Join key is `(WORK_RECOMMENDATION_DTL_ID, mp_id)` → `work_ref`.** Never `WORK_ID`, which
  is 82% null and issued only at completion.
- **480,768 raw stage rows** = 3,987 MP-level summary rows + 476,781 work-stage rows →
  **210,993 distinct works** (210,987 after dropping 6 with amount ≤ 0). The deck's
  210,993 and the package's 210,987 are *both* right; the FRD's "208k" is wrong.
- **There is no sanction date.** `Works Sanctioned` rows carry a verbatim copy of
  `RECOMMENDATION_DATE` (100.00% identical across 179,676 works). Presence is testable;
  timing is unknowable.
- **Censoring anchor is `max(RECOMMENDATION_DATE)` = 2026-05-26.** Anchoring on
  `max(all dates)` lands in 2044 and inflates every open work's duration by ~18 years.
- **695 works have no recommendation row** (orphans); **70 are completed without a sanction
  record**; **1,193 are back-dated**; **9 have out-of-window completion dates**. Carry and
  flag all of them — several are conformance signals, not defects.
- **`ACTIVITY_NAME` is a composite**: `WS/MP<code>/<FY>/<serial>-<official category>`.
  Parsing it yields **118 official permissible-works categories covering 93% of rows** — a
  free, interpretable peer axis. Do not treat it as 180k free-text values.
- **No district column exists.** `IDA_NAME` is a district *office*; `CONSTITUENCY` is a
  constituency. Never claim district-level results.
- **All Rajya Sabha works share `CONSTITUENCY = "Sitting Rajya Sabha"`.** Peer and travel
  grouping must key on state + constituency, never constituency alone.
- **DO NOT USE:** `ACTUAL_AMOUNT`, `WORK_ID`, `AVERAGE_RATING`, `FILE_STATUS`, `Sno`,
  `MP_NAME`, `Total_Amt` at work grain.
